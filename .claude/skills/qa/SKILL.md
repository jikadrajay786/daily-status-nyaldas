# QA: try to break it

Run this once a feature is finished and `spartan-quality-gate` passes. The gate proves the code compiles. This proves the feature works, and your job here is to find what doesn't. Passing the happy path is not a result.

Typos, copy tweaks and refactors with no behaviour change skip this. A small change gets a smaller matrix, not a skipped one.

## Safety first

- **Everything destructive or heavy runs on the local stack** (`supabase start`, `http://127.0.0.1`). Never run load tests, seed data, or create accounts on the live project (`ujdhkwaqvsgjyjfzszya`): real staff use it. Read-only checks there need the user's OK.
- Test accounts are generated by the test, on the local stack only. Never use real passwords or keys.
- No real side effects: local email goes to the stack's mail catcher, and `notify_url`/`notify_secret` stay unset so no push is sent. To test push sending, point `notify_url` at a local stub.
- Scripts and test data that won't be kept go in the scratchpad. Install tools there too (Playwright, load tools), not in the repo's `package.json`.

## 1. Scope

Read the diff (`git diff --stat`, then the relevant files) and the request. List what changed for users, what data and permissions it touches, and what existing behaviour could break. Trace callers of anything shared: `packages/core` and `packages/editor` changes hit both apps.

## 2. Write the test matrix

Before testing, write out each case with its expected result. Go through every section below and mark what doesn't apply as `n/a` with a reason. Expected results come from the request and CLAUDE.md, not from what the code currently does.

**Functional**: the main flow on each app, every button and state (empty, loading, error, full), save → reload → still there, change on one device → appears live on the other, cancel and back halfway through.

**Roles**: run every action as `user`, `manager`, `admin` and signed out. Check both what the UI hides and what the API refuses, and that a manager only reaches their own tasks and staff names.

**Edge cases**

- Input: empty, whitespace only, very long, emoji, Hindi/Gujarati conjuncts, pasted rich text, HTML and script tags, SQL-looking text, Hindi/Gujarati digits.
- Dates: today vs IST midnight, a device in another time zone, Sunday, a holiday, month and year ends, leap day, the 2-day edit lock boundary, days before joining, ranges that overlap or run backwards.
- Numbers: 0, negative, half values, maximum, non-numeric.
- Timing: double tap, two devices saving together, a stale screen acting on deleted data, a role changed while signed in, session expiring mid-action.
- Network: offline, slow, dropped mid-save, reconnect. The user sees a friendly translated error (`errMsg`), keeps what they typed, and nothing saves twice.
- Lifecycle: app backgrounded or locked mid-form, a draft surviving a restart, sign out and in as someone else with no leftover data.

**Language and display**: all of en/hi/gu with long strings, every theme and accent, largest text size (`3xl` on desktop, 2x on phones), high contrast, reduced motion, phone width, keyboard open.

**Accessibility**: keyboard-only on desktop with visible focus, screen reader labels and live announcements, pressables keep role and label, selection shown by more than colour.

**Security**

- RLS: call Supabase directly with the anon key and another user's JWT, bypassing the UI. Try reading, inserting, updating and deleting other people's rows, and calling each RPC with others' ids. A blocked write may return success with zero rows, so check the row afterwards.
- Privilege: changing `role`, `user_id`, `created_by`, or a protected column through direct updates; assignees editing beyond `status`.
- Injection: stored XSS in every rich-text and plain-text field, on both apps; non-http(s)/mailto links; `data-color` outside the palette; deep links with bad ids.
- Electron: all new IPC input validated in main, nothing new on `window.api` beyond need, CSP unchanged or justified.
- Exposure: emails and personal data in responses, logs, URLs and push payloads; no secrets in bundles or `VITE_` vars; Edge Functions reject a missing or wrong secret.
- Abuse: oversized payloads, repeated requests, replayed codes.
- Run the `security-review` skill on the diff as well.

**Load**: see step 5.

**Regression**: the neighbouring features that share code or tables with this one.

## 3. Automate

Add lasting tests for the matrix wherever a test can hold them:

- Logic: `packages/core/test` (Vitest).
- RLS, triggers, RPCs, concurrency: `packages/core/test-db` (`*.db.ts`), which refuses to run on anything but a local URL.

```bash
supabase start
```

If `supabase/config.toml` is missing, run `supabase init` first and don't commit it unless asked. Then pass `API_URL`, `ANON_KEY` and `SERVICE_ROLE_KEY` from `supabase status -o env` as these variables:

```bash
SUPABASE_URL=... SUPABASE_ANON_KEY=... SUPABASE_SERVICE_ROLE_KEY=... npm run test:db -w @daily-status/core | tail -n 30
```

Point test runs at a migrated database, and include any new migration. Confirm a new test fails when the behaviour is broken, so it isn't passing by accident. Check a re-run of each new migration too: they must be idempotent.

## 4. Run the real app

Tests don't replace using it. Look at the actual screens, with screenshots as evidence.

- **Desktop**: Playwright's Electron driver with `--user-data-dir` (or quit `npm run dev` first, or localStorage silently won't persist), and `ELECTRON_RUN_AS_NODE` unset. For hover, timers or transitions keep the window on top with `setBackgroundThrottling(false)`.
- **Mobile**: a dev build (`npm run ios` / `npm run android`, never Expo Go) on a simulator or emulator, using the iOS Simulator tool. Check the editor with the keyboard up.
- Point both at the local stack for anything that writes.
- Watch the console and network for errors, including ones the UI hides.

If an app or platform can't be run here (Android with no emulator, Windows, push on a real phone), mark those rows `not tested` and say what the user must check.

## 5. Load test

Local stack only. Size it from the feature, not a fixed number: at least 10× a realistic team, and the data a few years of use would produce.

- **Volume**: seed through the service role or SQL, for example 500 staff and 100,000 updates, then time the feature's queries. Use `EXPLAIN ANALYZE` on the slow ones, looking for sequential scans and N+1 calls.
- **Concurrency**: simulate many signed-in users at once against PostgREST and RPCs with real per-user JWTs, since RLS cost is part of the result. k6 through Docker needs no install; the stack is at `host.docker.internal`:

```bash
docker run --rm -i --add-host=host.docker.internal:host-gateway grafana/k6 run - < "$SCRATCH/load.js"
```

- **Races**: fire the same write 50 times with `Promise.all`, then check the invariant (one row, correct balance, no overlap). Keep these in `test-db`.
- **Client**: long lists stay smooth at 1,000+ rows, requests don't overflow URL limits, and realtime bursts don't cause refetch storms.

Default bar unless the feature calls for another: no 5xx or lost writes, p95 under 500 ms for reads and 1 s for writes, no sequential scan on a growing table. Local numbers show relative cost and bottlenecks, not production capacity: say so in the report.

## 6. Handle what you find

Reproduce it, write a failing test, fix it if it's clearly a bug in this feature, then rerun the gate and the affected matrix rows. Don't weaken a test or an expected result to get a pass. If the right behaviour is a product decision, or the fix is outside this feature, report it and leave it.

Clean up afterwards: stop background processes and delete scratch data. Leave the local stack running only if asked.

## 7. Report

```
QA: <feature>   Verdict: PASS | PASS WITH ISSUES | FAIL
Tested on: desktop mac / iOS sim / local stack @ <commit or "uncommitted">

Area         Pass  Fail  Not tested
Functional   12    0     0
...

Bugs
[High] Manager can read another manager's task: steps, expected, actual, fix status

Load: scenario, volume, p95, errors, bottleneck
Not tested: what and why, and what the user needs to check
```

Severity: **Critical** is data loss, a security hole or a crash on a main flow. **High** is a broken feature with no workaround. **Medium** has a workaround. **Low** is cosmetic.

Rules for the report:

- Only report what you ran. "Should work" and "looks correct from the code" count as `not tested`.
- No exhaustive claims. "Every scenario" is the aim; the matrix shows what was actually covered.
- FAIL on any open Critical or High. A failing or skipped row never rolls up into PASS.
